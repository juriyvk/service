# CRM и модель доступа

Существующий HTML/CSS остаётся основой. `app.js` заменяет демо-логику серверными операциями; localStorage не используется. В браузере нет роли-переключателя, service key и Supabase прямого клиента.

| Возможность | employee | deputy | manager |
| --- | --- | --- | --- |
| Видеть задачи | Автор или исполнитель | Все | Все |
| Создавать поручения | Себе | Активному сотруднику | Активному сотруднику |
| Принимать | Только исполнитель | Только исполнитель | Только исполнитель |
| Обновлять прогресс/статус после принятия | Исполнитель | Все | Все |
| Завершать review / отменять | Автор в пределах доступа | Все | Все |
| Контрольные точки | Создаёт автор, отмечает исполнитель | Все | Все |
| Комментарии и история | По доступной задаче | Все | Все |
| Проекты | Свои и связанные с доступной задачей | Создание и все проекты | Создание и все проекты |
| Библиотека | Только собственная | Только собственная | Только собственная |
| Управление сотрудниками | Нет | Нет | Административно вне UI |

Цепочка статусов: `pending → accepted → in_progress → review → done`. Из review возможен возврат в работу. Автор/руководство может отменить незавершённую задачу. Done и cancelled терминальные. «Просрочено» вычисляется отдельно по дате. Принятие записывает время. Завершение выставляет 100%, требует закрытия всех точек. SQL блокирует строку задачи, проверяет optimistic version, сохраняет history и outbox в одной транзакции. Комментарии и точки также пишутся в history; изменение прогресса с тем же статусом разрешено. Файлы не записываются в историю задач, их библиотека личная.

`telegram-auth` совместим с прежним gate, но не выдаёт браузеру авторитетную роль или постоянную сессию. `crm` заново проверяет initData и реестр. Браузерные p_actor/role не используются: SQL получает actor из проверенного Telegram ID. Статусы, видимость и назначение проверяются SQL, а не кнопками. HMAC payload с ролью всё равно не меняет запись employee. Поддержка блокировки через `active=false` применяется на следующем запросе.

Webhook проверяет независимый secret, private chat, sender/chat совпадение и активность. Бот вызывает те же SQL операции. Worker использует отдельный секрет и не принимает actor от клиента. Роли из текстов сообщений не интерпретируются. Файлы сохраняются под сгенерированным UUID, имя не входит в storage path. URL скачивания выдаётся владельцу на 60 секунд.

Проверки в репозитории: криптография с синтетическими подписями, SQL в PostgreSQL/WASM (PGlite с тестовым Storage schema stub), Edge Request/Response с mock сети, Playwright с mock Telegram и API. Реальные персональные данные, токены и production-сеть в тестах не используются. PGlite исполняет настоящий PL/pgSQL, но не проверяет платформенную настройку PostgREST/Storage, Telegram delivery и Deno runtime; это покрывает staging-приёмка из DEPLOY.md.
