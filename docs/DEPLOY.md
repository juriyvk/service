# Развёртывание СЕРВИС | ДВФМ

Изменения продолжают существующий `index.html`, сохраняют брендбук и адрес Supabase. Не публиковать HTML раньше сервера. Ветка `feat/secure-crm-core`, без автоматического слияния и без изменений production.

## Что известно о прежней авторизации

В исходном `index.html` выполнялся POST `{initData}` в `telegram-auth`, ожидался `{ok, employee:{full_name,role}}`. Исходника функции, схемы сотрудников, RLS и Secrets в репозитории не было. Клиентский gate проверял только вход; операции с задачами были демо в localStorage. Новый `telegram-auth` сохраняет контракт, но читает **новый** реестр `dvfm.employees`. Доступ прежних сотрудников нельзя считать автоматически перенесённым. До переключения проверить существующую функцию и источник сотрудников в Supabase Dashboard, сделать резервную копию функции/конфигурации, затем сопоставить записи в staging. Токены и реальные записи не копировать в репозиторий, тесты, PR или логи.

## 1. Staging и миграция

1. Создать резервную копию production и отдельный Supabase staging-проект. Сначала проверить `npm ci`, `npm test`, `npm run check`, `npm run test:browser` (Chromium в `CHROMIUM_PATH`). Для настоящего Supabase выполнить `supabase start` и `supabase db reset` локально либо `supabase db push --linked` в staging после просмотра `supabase db push --dry-run`.
2. Миграция `202611120001_crm.sql` добавляет схему `dvfm`, четыре RPC и приватный bucket. Старые таблицы не изменяются. Не запускать её вручную повторно: учёт версии ведёт Supabase CLI. При существующем публичном `dvfm-private` транзакция завершится ошибкой. Проверить также лимит и MIME уже существующего bucket.
3. Схема `dvfm` **не должна входить в Exposed schemas** PostgREST. В `public` доступны лишь RPC, EXECUTE отозван у `PUBLIC/anon/authenticated`, выдан `service_role`. Сервисный ключ не передавать браузеру. На таблицах включён RLS без клиентских разрешений; restrictive Storage policy блокирует доступ клиентов к этому bucket даже при старых широких permissive policies. Storage использует service role только на сервере.
4. Через SQL Editor, в закрытой административной сессии, вне Git, создать реестр сотрудников из **проверенного** существующего источника. Поля: `telegram_id bigint unique`, `full_name`, `role` строго `manager/deputy/employee`, `active`. Не использовать имя пользователя Telegram как идентификатор. Старую роль `admin` сопоставлять с `manager` только по утверждённому списку; автоматического повышения нет. Первый manager создаётся вручную. Пример параметризованного запроса для административного скрипта: `insert into dvfm.employees(telegram_id,full_name,role) values($1,$2,$3)`; реальные параметры вводятся только локально. Не импортировать демо localStorage.
5. Сверить число активных записей и соответствие Telegram ID, проверить manager, deputy, employee и отключённого сотрудника с отдельным staging-ботом. Интерфейс управления сотрудниками намеренно отложен на последний этап после приёмки и проверки прав.

## 2. Secrets и функции

Использовать Supabase Dashboard → Edge Functions → Secrets либо `supabase secrets set --env-file /private/path/staging.env`. Файл держать вне репозитория. Не вводить секреты в аргументы команд, PR и чат.

| Secret | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен соответствующего staging/production-бота |
| `ALLOWED_ORIGINS` | Точные HTTPS origins Mini App через запятую, без завершающего `/` |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный независимый секрет 32+ символа, только A-Z/a-z/0-9/_/- |
| `TELEGRAM_MINI_APP_URL` | Именованная ссылка BotFather: `https://t.me/<bot>/<app>` |
| `OUTBOX_WORKER_AUTH` | Полная строка `Bearer <случайный независимый секрет>` для worker |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` предоставляет Supabase runtime. Никогда не помещать service key, bot token или webhook secret в `app.js`.

```sh
supabase functions deploy telegram-auth
supabase functions deploy crm
supabase functions deploy telegram-webhook
```

В `supabase/config.toml` для этих функций отключён gateway JWT: Telegram не выдаёт Supabase JWT. Это **не** публичная авторизация: `telegram-auth/crm` проверяют HMAC initData и сотрудника при каждом запросе; webhook проверяет `X-Telegram-Bot-Api-Secret-Token`, worker — отдельный Authorization. Подпись, возраст (до 1 часа), будущее время, дубли полей и Telegram ID проверяются до DB. CORS ограничен точными origins; он не заменяет аутентификацию. initData не сохраняется в localStorage и логах. Это краткоживущий bearer credential: TLS и защита от XSS обязательны; повторное использование в течение часа допускается для запросов Mini App. После истечения нужно открыть Mini App заново.

Проверить `deno check supabase/functions/{telegram-auth,crm,telegram-webhook}/index.ts` в окружении Deno/Supabase. Локальная `npm run check` проверяет TypeScript с минимальными декларациями Deno, а тесты Edge запускают транспилированные обработчики с mock RPC. Это не заменяет staging-запуск настоящего Edge Runtime и Storage.

## 3. Mini App и Telegram webhook

1. В staging-копии изменить **только** `base` в `app.js` на staging Supabase URL. Два статических файла `index.html` и `app.js` должны раздаваться по HTTPS с одного origin. Для production оставить существующий Supabase URL после проверки project ref. Сохранить прежнюю публикацию для отката. Убедиться, что GitHub Pages не публикует feature-ветку автоматически.
2. В BotFather настроить именованное Mini App и кнопку меню на существующий HTTPS адрес. Проверить совпадение бота с `TELEGRAM_BOT_TOKEN`. `startapp=task_<UUID>` открывает карточку; параметр выбирает экран, **не предоставляет права**.
3. Выполнить Telegram `setWebhook` из закрытого административного окружения: POST JSON `{url: "https://<ref>.supabase.co/functions/v1/telegram-webhook", secret_token: <secret>, allowed_updates:["message"]}`. Токен читается из защищённой переменной, URL API содержит токен: не логировать запрос/исключения. Проверить `getWebhookInfo` без публикации токена. Не включать `drop_pending_updates` при переключении без решения о судьбе очереди.
4. Принимаются только личные сообщения зарегистрированных активных сотрудников. Текст без команды создаёт задачу себе. `/task self | Название | 2030-01-01`; руководство может заменить `self` UUID сотрудника из раздела «Справка». Роли и исполнитель проверяются SQL. Нераспознанные команды возвращают справку. Задачи дедуплицируются по `update_id` в той же транзакции. Документы сохраняют резервирование пути для повторной загрузки при retry. Telegram `sendMessage` не имеет idempotency key: редкие дубли уведомлений после сбоя сети возможны.
5. Настроить приватный scheduler (Supabase Cron + Vault/Edge invocation или внешний cron) раз в минуту: POST `https://<ref>.supabase.co/functions/v1/telegram-webhook?worker=1`, header `Authorization` из `OUTBOX_WORKER_AUTH`. Значение хранить в Vault/secret store, не в миграции. Он обрабатывает уведомления от Mini App и повторные доставки. Без scheduler уведомления Mini App останутся в outbox до следующего webhook.

Очередь использует `FOR UPDATE SKIP LOCKED`, lease 90 секунд, до 20 записей за вызов, 10 попыток, повтор через 2 минуты. Для большого потока уменьшить batch/увеличить частоту и проверить время выполнения Edge. Мониторить `dvfm.outbox` с `sent_at is null`, `attempts>=10` и просроченными lease; после устранения причины администратор вручную сбрасывает attempts/available_at. Бот должен быть запущен сотрудником; блокировка бота приводит к повторным попыткам. Для вывода персональных задач исключить групповые чаты.

## 4. Обязательная staging-приёмка перед production

- Существующий зарегистрированный сотрудник входит; неизвестный, отключённый, устаревшая/изменённая подпись получают отказ. Подмена browser role/id не даёт прав. Проверить реальный deploy старой функции до замены и нового контракта после.
- Employee создаёт только себе; manager и deputy — активным сотрудникам. Исполнитель принимает только своё поручение; переходы и конфликт version контролирует DB. Employee не завершает поручение руководителя без проверки. Незакрытые контрольные точки блокируют done.
- Прямые anon/authenticated REST/RPC/Storage запросы, чужая task UUID, document UUID и deep link не дают доступ. Руководство тоже не читает чужую приватную библиотеку. Подписанная ссылка — bearer ссылка на 60 секунд; её не публиковать.
- Проверить загрузку PDF/DOCX/XLSX, границу 10 МиБ, запрещённый MIME, download и истечение ссылки в реальном Storage. MIME allowlist не является антивирусом; перед массовым внешним импортом нужен отдельный карантин/сканирование. Не открывать HTML/SVG; они запрещены.
- Проверить реальный webhook с неправильным secret, повтор одного update_id, документом, уведомлением и кнопкой deep link на iOS/Android Telegram. Проверить cron после изменения задачи из Mini App, недоступность Telegram и retry.
- Визуальная проверка на узком экране, чтение/создание задачи, справка, аналитика. Аналитика ограничена доступными задачами. HR-заявки не реализованы: бывший макет обозначен в справке, фиктивная отправка удалена.

## 5. Откат и эксплуатация

Откатить статические файлы и Edge Functions на сохранённые версии; вернуть прежний webhook при необходимости, остановить scheduler. Новые таблицы **не удалять**: сохранить задачи/историю/документы и резервную копию. Откат UI к прежнему localStorage-макету не показывает новые серверные задачи. SQL migration транзакционная; не редактировать применённую миграцию — выпускать следующую.

Срок хранения истории, документов и `bot_updates` согласовать с владельцем данных. Не чистить bot_updates раньше допустимого окна повторной доставки Telegram (минимум несколько суток); иначе повтор создаст задачу. Резервирования документов без ready после ошибок требуют периодической административной очистки вместе с orphan Storage objects. Нет автоматического удаления/приглашений, переадресации задач и загрузки произвольных интернет-URL. Для первого релиза snapshot возвращает все доступные записи; перед большим объёмом внедрить пагинацию и серверные агрегаты.
