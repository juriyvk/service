# Двусторонняя синхронизация CRM ↔ YouGile

Реализована связь одного существующего проекта CRM с одной доской существующего проекта YouGile. Фирменный интерфейс и Telegram-вход сохраняются. Настройки находятся в «Справка → Синхронизация YouGile» и доступны только действующему manager/deputy. Роль проверяется в БД при каждом запросе. Привязка уже существующих сотрудников не создаёт новых сотрудников.

Реальная связка ещё не включена. При проверке доступности известные адреса Supabase отвечали NXDOMAIN; восстановление проекта и актуальный URL должен подтвердить владелец в Dashboard. Не создавайте проект заново и не запускайте повторно первоначальный staging-setup.sql. Подробности — [CONNECTION-INCIDENT.md](CONNECTION-INCIDENT.md).

## Что синхронизируется

| Поле CRM | Поле YouGile | Правило |
| --- | --- | --- |
| Название | title | До 240 символов |
| Описание | description | Текст до 10000 символов; исходящая HTML-разметка экранируется |
| Ответственный | assigned | Один явно сопоставленный пользователь |
| Статус | columnId / completed | Явное сопоставление колонок; completed=true означает done |
| Срок | deadline | Календарная дата в Europe/Moscow |

Новые задачи CRM экспортируются, а новые задачи выбранных колонок YouGile импортируются при отдельно включённом «Импортировать новые задачи». Совпадение названий не связывает существующие задачи автоматически. Перед первым включением проверьте, нет ли копий задач в обеих системах: такие записи считаются разными. Импорт исходного статуса всегда начинается с pending; принятие выполняет исполнитель в CRM. Задача YouGile, уже находящаяся в работе/на проверке/готово, создаёт вопрос для ручного разрешения после принятия и допустимых переходов.

Прогресс, контрольные точки, комментарии, документы, права и записи сотрудников остаются в CRM. История входящих изменений сохраняется с действием yougile.pull, уведомления поступают в существующую outbox. Синхронизация идёт от полномочий руководителя, сохранившего настройки; отключение его доступа останавливает worker.

Облачный API YouGile не подтверждает личность автора каждого изменения задачи для этой интеграции. Доступ к выбранной доске и права владельца API-ключа задают доверенную внешнюю область. Не выдавайте доступ к доске тем, кому нельзя менять синхронизируемые задачи.

## Статусы и ограничения

| CRM | Типичная колонка YouGile |
| --- | --- |
| pending / accepted | Новые |
| in_progress | В работе |
| review | На проверке |
| done | Готово |
| cancelled | Отдельная необязательная колонка |

accepted не экспортируется как отдельная колонка и сохраняется при входящем «Новые». YouGile не принимает задачу за исполнителя. Завершение через YouGile проходит те же обязательные переходы и проверку незакрытых контрольных точек. Завершённые и отменённые задачи нельзя открыть заново синхронизацией. Смена ответственного требует pending и сбрасывает принятие.

«Ожидает ответа» не имеет соответствия в текущей модели CRM: перемещение связанной задачи туда создаёт конфликт области. Отмена без настроенной отдельной колонки требует решения руководителя. Удаление, архивирование и перемещение за пределы связи не удаляют задачу другой системы. Несколько ответственных, отсутствующая привязка пользователя и изменение локальной даты при внешнем сроке со временем также требуют внимания. Время существующего срока YouGile не стирается молча.

Описание синхронизируется как текст, без преобразования редактора форматирования YouGile. Нативные HTML-теги могут отображаться в CRM текстом. Для форматированных документов используется отдельная приватная библиотека.

## Очередь и конфликты

Таблицы yg_config, yg_users, yg_links, yg_dirty, yg_log находятся в закрытой схеме dvfm. Включены RLS; anon/authenticated не имеют прав к таблицам и RPC. Доступ — только через сервер с проверкой Telegram initData либо worker-secret. Browser role, URL API и ID проекта из произвольного тела запроса не определяют права.

Локальные изменения попадают в транзакционную очередь. Каждая пара задач хранит подтверждённые снимки обеих сторон. Независимые изменения разных полей объединяются; изменение одного поля обеими сторонами останавливает эту пару до выбора «Оставить CRM» / «Принять YouGile». Выбор привязан к ID конфликта, версии CRM и наблюдавшемуся состоянию YouGile; новые изменения требуют повторного решения. «Повторить после исправления» заново проверяет снимки, не выбирая победителя и не сбрасывая базовую историю.

Создание использует постоянный idempotencyKey. Потерянный ответ повторяется с тем же ключом; импорт новых внешних записей временно приостанавливается, пока есть неподтверждённое создание, чтобы не импортировать собственный экспорт как вторую задачу. Подтверждение старой версии не удаляет более новую работу из очереди. Входящие изменения подавляют повторную отправку. Ошибки сети повторяются через две минуты, до десяти неудач; затем требуется ручной повтор.

Worker имеет общую блокировку на две минуты, лимит 30 внешних запросов в календарную минуту и бюджет запуска около 45 секунд. Обрабатывает небольшие порции очереди, проверяет связанные задачи по ID (включая ушедшие с доски) и обходит выбранные колонки страницами по пять задач. При Cron раз в минуту синхронизация постепенная: большие доски и очереди требуют нескольких проходов. Собственные интеграции компании расходуют общий лимит YouGile отдельно; осмотр/настройка из интерфейса тоже выполняют чтение API.

Перед записью worker повторно читает YouGile и проверяет текущую локальную версию, после записи проверяет результат. Официальный API PUT /tasks/{id} не документирует условную запись по версии/ETag, поэтому узкую гонку между последним GET и PUT полностью устранить нельзя. Изменяются только необходимые поля, а выявленные расхождения останавливаются как конфликт; абсолютная гарантия сохранения одновременной правки в этом промежутке невозможна. При массовом первоначальном переносе избегайте параллельной правки одних полей.

## Включение на существующем staging

1. Проверьте доступность проекта Supabase в Dashboard и актуальность Project URL. Нужны уже применённые обе CRM-миграции и рабочий вход через тестового бота. Сначала восстановите эту основу.
2. Примените **одним запуском** [staging-upgrade-yougile.sql](staging-upgrade-yougile.sql) в SQL Editor существующего staging. Скрипт транзакционный, добавляет только новые объекты, проверяет историю и регистрирует миграцию 202611260001. Повторное применение отклоняется. Не запускайте одновременно эту копию и canonical migration. При работе через CLI вместо копии используется supabase/migrations/202611260001_yougile_sync.sql с обычным учётом Supabase migrations.
3. В Supabase Secrets сохраните YOUGILE_API_KEY, YOUGILE_PROJECT_ID и YOUGILE_BOARD_ID. Используйте минимальные необходимые права выбранного проекта. Ключ — только в Secrets, без префикса Bearer; сервер добавляет его сам. Подключение YouGile в ChatGPT не выдаёт API-ключ серверу Mini App. Значение YOUGILE_SYNC_ENABLED сначала false. YOUGILE_API_BASE необязателен, по умолчанию https://ru.yougile.com/api-v2.
4. Разверните Edge Function yougile из [standalone-файла](../deploy/dashboard/yougile.ts) с Verify JWT disabled. Авторизацию обеспечивает обработчик. Для CLI используйте canonical source и существующий config.toml. Пересобранный staging-telegram-setup понадобится только для настройки Cron.
5. Опубликуйте согласованные файлы preview/staging/index.html, app.js и yougile-ui.js в staging/ через отдельный PR. Все файлы одной сборки перечислены в manifest.json. Корневую production-страницу на этом этапе не меняйте.
6. Руководитель открывает «Справка → Синхронизация YouGile → Настройки связи», выбирает существующий проект CRM и колонки. Оставьте оба переключателя выключенными, сохраните и явно сопоставьте существующих сотрудников по UUID. Поддерживаются прямые участники проекта YouGile, кроме observer и удалённых; доступ, унаследованный только через подразделение, пока не разворачивается. Имена не используются как идентификаторы.
7. Проверьте состав проекта: включение экспортирует все его текущие задачи, а включение импорта создаёт новые CRM-задачи для несвязанных внешних записей в выбранных колонках. Сначала используйте отдельный согласованный тестовый проект/доску и синтетические задачи. После проверки области включите связь и нужный импорт в интерфейсе, затем YOUGILE_SYNC_ENABLED=true в Secrets. Нажатие «Синхронизировать» запускает один проход.
8. Для автоматического режима примените [staging-install-yougile-worker.sql](staging-install-yougile-worker.sql). В Dashboard Test функции staging-telegram-setup: POST {"action":"configure_yougile_worker"}, заголовок Authorization — **полное текущее** значение OUTBOX_WORKER_AUTH, включая Bearer и пробел. Это создаёт отдельное задание dvfm-staging-yougile каждую минуту. Секрет хранится в Vault и не попадает в cron-команду. Этот SQL и helper предназначены только для staging.
9. Проверьте создание в обе стороны, изменение разных полей, конфликт одного поля, принятие, контрольные точки, смену роли/отключение сотрудника и потерю сетевого ответа. Посмотрите очередь и конфликты. Новые роли сотрудников через связку не назначаются. После установки helper можно удалить.

При смене OUTBOX_WORKER_AUTH обновите секрет, затем заново вызовите нужный configure_worker/configure_yougile_worker: конфигуратор обновляет общее значение в Vault. При смене TELEGRAM_WEBHOOK_SECRET повторно вызывается configure для регистрации webhook с новым значением. Переписывать код из-за ротации Secrets не требуется.

Остановка: сначала YOUGILE_SYNC_ENABLED=false; затем выключите связь в интерфейсе и отключите только job dvfm-staging-yougile. Это не выключает уведомления. Данные и соответствия сохраните: откат удалением таблиц приводит к потере связей и опасности повторного импорта. Менять область и уже использованные соответствия колонок/пользователей интерфейс не позволяет; перенос требует отдельной миграции.

## Проверки и контракт

npm test проверяет подпись Telegram, права, RLS, миграции, переходы, очередь, повтор после потерянного ответа, двустороннее обновление, конфликты и бюджет запросов. npm run check и npm run check:edge проверяют исходники и совпадение standalone/preview/SQL-сборок. Браузерные проверки включают существующий вход и экранирование данных YouGile. Все данные тестов синтетические; реальных сотрудников и ключей в репозитории нет.

Официальные источники: https://ru.yougile.com/api-v2 , схема https://ru.yougile.com/api-json , https://docs.yougile.com/docs/admin-guide-linux/api/ . Используются GET projects/{id}, boards/{id}, columns, task-list, tasks/{id}, POST tasks с idempotencyKey и PUT tasks/{id}; автоматическое удаление и архивирование отсутствуют.
